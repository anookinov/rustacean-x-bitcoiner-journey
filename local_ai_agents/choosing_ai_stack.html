Rustacean X Bitcoiner Journey

Choosing the AI Stack

Choosing an AI development stack is a statement about values as much as a technical decision. This page documents why I chose open-source model serving (Ollama), a multi-agent VS Code extension (Roo Code), and Claude Code as the senior supervising agent — and why this combination fits a Bitcoiner and Rustacean mindset.

In this guide, you will:

  • Understand why local model serving aligns with self-sovereignty principles
  • Evaluate model serving options and choose Ollama
  • Select code-focused open-source models appropriate for CPU-only inference
  • Compare VS Code AI extensions and understand why Roo Code fits an orchestrator workflow
  • Define Claude Code’s role as the senior agent in the pipeline

Why Local AI Models?

Running AI models locally follows the same reasoning as running your own Bitcoin node: you eliminate dependency on a third party for a resource you need to control.

With a cloud-only AI setup:

  • Every prompt leaves your machine — code context, architecture decisions, internal notes
  • Availability depends on the provider’s uptime and pricing
  • Rate limits and token costs constrain exploratory usage
  • The provider can change terms, raise prices, or deprecate models

With a local model setup on the same hardware that runs your Bitcoin stack:

  • Prompts never leave your LAN for routine tasks
  • No per-token cost for local inference (electricity only)
  • Always available, even offline
  • Models are files you own and can pin to specific versions
  • The cloud (Claude Code) is reserved for high-value final review, keeping cloud costs low

The tradeoff is inference speed. The Minisforum X1-255 has no dedicated GPU, so inference runs on CPU. A 7B-parameter model produces responses in roughly 10–30 seconds — acceptable for background agents handling drafts and refactoring, not suitable for real-time autocomplete. I use local models for agentic tasks (multi-step file editing) and Claude for interactive review.

Chosen: Ollama

Ollama installs as a systemd service on Ubuntu, exposes an OpenAI-compatible REST API, and includes a built-in model registry. It starts automatically on boot, recovers from crashes, and is the easiest path to a headless model server on a Proxmox VM. LM Studio requires a GUI (not viable on a headless Ubuntu VM). Direct llama.cpp is powerful but requires more manual setup with no service management.

Choosing Code-Focused Models

Rust is a harder target

Rust taxes AI models in ways that most languages do not: lifetime annotations, borrow checker enforcement, trait bounds, async runtimes, and unsafe rules all require a level of structured reasoning that smaller models handle inconsistently. No local model currently matches Claude Sonnet/Opus 4.6 on complex Rust, but the gap is narrowing — particularly with 14B+ models on reasoning-heavy tasks. The practical approach is to lean on local models for drafting and boilerplate, and reserve Claude for lifetime errors, trait design, and final review.

🖥️ RAM Planning: Ollama loads a model into RAM on first request and keeps it resident until an idle timeout (default 5 minutes). With 16 GB VM RAM and Ubuntu using ~1.5 GB, roughly 14.5 GB is available for models. qwen2.5-coder:7b and qwen2.5-coder:14b both fit comfortably. Running two models simultaneously is possible at 7B; at 14B it gets tight.

⬆️ If you add a GPU later: qwen2.5-coder:32b becomes the best practical local option for Rust. llama3.3:70b is also excellent but requires ~40 GB VRAM or a large unified-memory system.

Recommended starting set:

  • qwen2.5-coder:14b — primary code agent; best CPU-practical quality for Rust (upgrade from 7B if RAM allows)
  • qwen2.5-coder:7b — fallback when speed matters more than depth
  • llama3.1:8b — planning/architecture agent (stronger general reasoning than pure code models)

You can swap models at any time by changing the Ollama tag in Roo Code’s provider settings. The rest of the workflow stays the same.

Comparing VS Code AI Extensions

Several VS Code extensions support multi-model, multi-agent workflows. The distinguishing factor for this setup is whether the extension supports an Orchestrator mode — one agent that breaks a task into steps and delegates each step to a specialized sub-agent, potentially using a different model per sub-agent.

Chosen: Roo Code

Roo Code’s built-in Orchestrator mode is a direct match for this workflow. The Orchestrator agent reads a task, breaks it into sub-tasks, and delegates each to a specialized agent — each potentially backed by a different model. Architect mode uses a planning-focused model; Code mode uses a code-focused model; the final review is routed to Claude via the Anthropic provider. This is precisely the pipeline described in the architecture overview.

Continue.dev is excellent for inline autocomplete and quick chat but is not designed for multi-step agentic task delegation. It complements Roo Code for autocomplete (where low latency matters) but is not the right tool for orchestration.

Claude Code’s Role as Senior Agent

I already run Claude Code as a Pro subscriber — which means I have access to Claude (Sonnet/Opus-class models) via the CLI, already integrated into my development workflow. Roo Code supports a Claude Code provider that proxies model requests through the locally installed claude CLI, consuming Pro subscription allowance rather than per-token API credits.

The approach I use:

  • Roo Code routes most tasks to local Ollama models (Code, Debug, all verification modes)
  • Roo Code’s Orchestrator and Architect modes use the Claude Code provider — decomposition and design require senior judgment that 7–8B models handle poorly
  • Roo Code’s Code Reviewer mode uses the Claude Code provider as the final gate — full-context review and commit approval before any code lands

This keeps Claude reserved for the three stages where it genuinely matters, while local models absorb the bulk of the token work at zero cloud cost.

💡 Flexibility: The architecture is intentionally model-agnostic. Any Roo Code agent mode can be pointed at a different Ollama model, an OpenAI-compatible endpoint, or a different cloud provider at any time. The agent roles (Orchestrator, Architect, Code, Reviewer) are defined by their system prompts and tool access, not by the model powering them. Swap models freely as better open-source options become available.
