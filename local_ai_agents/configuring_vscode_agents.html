Configuring VS Code Agent Extensions

With Ollama running on the AI VM and accessible from my MacBook, this page wires it into VS Code through Roo Code — a VS Code extension that supports an Orchestrator mode, per-mode model selection, and agentic file editing. Each mode is configured with a distinct local Ollama model matched to the role’s demands: a reasoning model for planning and design, a code-specialized model for implementation and debugging.

VS Code’s process cannot route directly to LAN IP addresses on macOS in some configurations. The solution is a persistent SSH tunnel: autossh forwards localhost:11434 on the MacBook through SSH to Ollama on the AI VM. Roo Code connects to localhost, which always works. Port 11434 does not need to be exposed on the LAN — only SSH (port 22) is used.

In this guide, you will:

  • Install the Roo Code extension in VS Code
  • Set up a persistent autossh tunnel from the MacBook to the AI VM
  • Pull the Ollama models needed for reasoning and planning roles
  • Add named Ollama API configurations in Roo Code (one per model)
  • Assign a specific model to each built-in agent mode (Orchestrator, Architect, Code, Debug, Ask)
  • Test each mode to verify it generates responses from the expected model

Pre-requisites

Preparation

  • Ollama running on the AI VM at 192.168.1.101 with SSH access from the MacBook
  • qwen2.5-coder:7b already pulled in Ollama (from Installing Ollama and Models)
  • VS Code installed on your MacBook
  • Homebrew installed on your MacBook

Software

  • VS Code (latest stable release)
  • Roo Code extension (roo-cline.roo-cline in VS Code marketplace)
  • autossh (brew install autossh)

References

  • Roo Code documentation
  • Ollama OpenAI-compatible API docs

Step-by-Step Instructions

Step 1: Install Roo Code

  1. Open VS Code on your MacBook

  2. Open the Extensions panel: Cmd+Shift+X

  3. Search for Roo Code

  4. Find the extension by Roo Code (publisher: roo-cline) and click Install

  5. After installation, a Roo Code icon (🦘) appears in the VS Code Activity Bar on the left sidebar

  6. Click the icon to open the Roo Code panel

Step 2: Set up the Autossh Tunnel

autossh runs as a macOS launchd agent, forwarding localhost:11434 on the MacBook to Ollama on the AI VM through SSH. It starts at login and reconnects automatically if the AI VM restarts or the network drops.

  1. Install autossh:

    brew install autossh

  2. Create the launchd agent plist:

    cat > ~/Library/LaunchAgents/com.local.ollama-tunnel.plist << 'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.local.ollama-tunnel</string>
    <key>ProgramArguments</key>
    <array>
        <string>/opt/homebrew/bin/autossh</string>
        <string>-M</string>
        <string>0</string>
        <string>-N</string>
        <string>-L</string>
        <string>11434:localhost:11434</string>
        <string>-o</string>
        <string>ServerAliveInterval=60</string>
        <string>-o</string>
        <string>ServerAliveCountMax=3</string>
        <string>-o</string>
        <string>ExitOnForwardFailure=yes</string>
        <string>ai@192.168.1.101</string>
    </array>
    <key>RunAtLoad</key>
    <true/>
    <key>KeepAlive</key>
    <true/>
    <key>StandardErrorPath</key>
    <string>/tmp/ollama-tunnel.log</string>
</dict>
</plist>
EOF

  3. Load the agent:

    launchctl load ~/Library/LaunchAgents/com.local.ollama-tunnel.plist

  4. Verify it is running:

    launchctl list | grep ollama-tunnel
curl http://localhost:11434/v1/models

    The launchctl output should show a PID in the first column (not -). The curl should return a JSON list of Ollama models.

💻 Intel Mac: Replace /opt/homebrew/bin/autossh with /usr/local/bin/autossh in the plist.

🔄 Reloading after plist changes: launchctl unload ~/Library/LaunchAgents/com.local.ollama-tunnel.plist && launchctl load ~/Library/LaunchAgents/com.local.ollama-tunnel.plist

Step 3: Add the Ollama API Configurations

Roo Code stores provider settings as named API Configurations — each is a saved profile with a provider type, base URL, and model. Assigning different models to different modes requires one configuration per model. Create three configurations, all pointing at the same Ollama server:

  1. In the Roo Code panel, click the Settings gear icon (⚙️) in the top-right corner

  2. Go to API Configuration and create the first profile:

    • Configuration name: ollama-coder
    • Provider: OpenAI Compatible
    • Base URL: http://localhost:11434/v1
    • API Key: ollama (any non-empty string; Ollama does not validate keys)
    • Model: qwen2.5-coder:7b
    • Save

  3. Create the second profile:

    • Configuration name: ollama-reasoning
    • Provider: OpenAI Compatible
    • Base URL: http://localhost:11434/v1
    • API Key: ollama
    • Model: qwen3:8b
    • Save

  4. Create the third profile:

    • Configuration name: ollama-architect
    • Provider: OpenAI Compatible
    • Base URL: http://localhost:11434/v1
    • API Key: ollama
    • Model: deepseek-r1:8b
    • Save

🌐 Provider URL: Use http://localhost:11434/v1 — the autossh tunnel (Step 2) forwards this to Ollama on the AI VM. The /v1 suffix is required; Ollama’s OpenAI-compatible endpoint lives at /v1/chat/completions.

📦 Three configs, one server: All three configurations point at the same tunnel endpoint. Three named profiles is the correct pattern — Roo Code uses the configuration name to distinguish which model to invoke when switching modes.

Step 4: Pull the Reasoning Models

The Orchestrator and Architect roles use reasoning-focused models different from the coding-specialized model. Pull them on the AI VM before configuring Roo Code.

  1. SSH into the AI VM:

    ssh ai@192.168.1.101

  2. Pull the two reasoning models:

    ollama pull qwen3:8b
ollama pull deepseek-r1:8b

  3. Verify all three models are available:

    ollama list

    You should see qwen3:8b, deepseek-r1:8b, and qwen2.5-coder:7b in the output.

💡 Model roles: qwen3:8b handles orchestration and general reasoning with a built-in thinking mode. deepseek-r1:8b uses chain-of-thought reasoning before answering, making it well-suited for architectural design decisions. qwen2.5-coder:7b remains the dedicated coding model. llama3.1:8b is no longer needed and can be freed with ollama rm llama3.1:8b.

Step 5: Assign API Configurations to Each Mode

Each mode is assigned one of the named API configurations created in Step 3. The configuration determines which model that mode uses:

ModePurposeAPI ConfigurationModel
OrchestratorBreaking tasks into sub-tasks, delegatingollama-reasoningqwen3:8b
ArchitectSystem design, planning, breaking down tasksollama-architectdeepseek-r1:8b
CodeWriting and editing code filesollama-coderqwen2.5-coder:7b
DebugDiagnosing errors and tracing issuesollama-coderqwen2.5-coder:7b
AskQuestions and explanations, no file editsollama-reasoningqwen3:8b

Custom verification and specialist modes (Quality Guard, Code Reviewer, etc.) are added in the Multi-Agent Workflow with Local AI Agents guide.

To assign a configuration to each mode:

  1. Click the mode selector (dropdown at the top of the Roo Code panel showing the current mode name)

  2. Select a mode (e.g., Architect)

  3. In the mode settings, click the API Configuration dropdown

  4. Select ollama-architect for Architect (or the configuration shown in the table for each mode)

  5. Repeat for all remaining modes following the table above

🔄 Flexibility: To swap a model for a role, edit the API configuration rather than changing each mode individually. All modes sharing that configuration update automatically.

Step 6: Test Each Mode

Test the Code mode (Ollama qwen2.5-coder:7b):

  1. Switch to Code mode in the Roo Code panel

  2. Open a Rust project (or any code file) in VS Code

  3. Send a prompt: Add a unit test for this function

  4. Roo Code should show the model name (qwen2.5-coder:7b) in the response header

  5. You will see the response stream in with a latency of ~5–15 seconds for a short response (CPU inference)

Test the Architect mode (deepseek-r1:8b):

  1. Switch to Architect mode

  2. Send a prompt: I need to build a CLI tool in Rust that monitors Bitcoin mempool fees and sends ntfy notifications. Outline the architecture.

  3. You will see a visible reasoning pass as DeepSeek R1 works through the problem, followed by a structured design document

Test the Orchestrator mode (qwen3:8b):

  1. Switch to Orchestrator mode

  2. Send a prompt: I want to add a fee alert feature to my Bitcoin monitoring tool. Break this down into sub-tasks and identify which agent should handle each.

  3. The Orchestrator decomposes the task and produces a delegation plan with acceptance criteria. Prepend /no_think to the prompt for a faster response without the reasoning pass.

⏱️ Response Times: All models run locally on CPU, producing ~10–25 tokens/second. A 200-token response takes roughly 8–20 seconds. deepseek-r1:8b includes a reasoning pass that adds latency before the visible response begins — this is expected behavior, not an error.

Step 7: Configure VS Code Settings for Roo Code

Open VS Code User Settings (Cmd+,) and add/verify these settings for a smooth Roo Code experience:

{
  "roo-cline.autoApproveReadOnly": true,
  "roo-cline.autoApproveWrite": false,
  "roo-cline.autoApproveExecute": false
}
  • autoApproveReadOnly: true — Roo Code can read files without prompting you each time
  • autoApproveWrite: false — you approve every file write (recommended until you trust the workflow)
  • autoApproveExecute: false — you approve every shell command execution

🛡️ Approval Settings: Starting with write and execute approvals required gives you explicit control over what the AI agents change on your machine. As you grow comfortable with specific task types, you can selectively enable auto-approval for lower-risk actions.

Troubleshooting

Roo Code shows “connection refused”, “fetch failed”, or “connection error” for Ollama:

  • Verify the tunnel is running: launchctl list | grep ollama-tunnel — the first column must show a PID, not -
  • Test the tunnel: curl http://localhost:11434/v1/models — if this fails, the tunnel is down
  • Reload the tunnel: launchctl unload ~/Library/LaunchAgents/com.local.ollama-tunnel.plist && launchctl load ~/Library/LaunchAgents/com.local.ollama-tunnel.plist
  • Check the tunnel error log: cat /tmp/ollama-tunnel.log
  • Verify Ollama is running on the AI VM: ssh ai@192.168.1.101 "ollama list"
  • All three API configurations must use http://localhost:11434/v1 as the Base URL — not the AI VM’s LAN IP

Model name not found error:

  • The model name in Roo Code must exactly match what ollama list shows (e.g., qwen2.5-coder:7b, not qwen2.5-coder)
  • Run ollama list in the AI VM to get exact names

Responses cut off mid-generation:

  • Ollama may have hit a context length or output token limit. Try a shorter prompt or switch to a model with a larger context window.
